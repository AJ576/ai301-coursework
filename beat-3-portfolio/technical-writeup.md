# Overhauling DataMapper's Choice Selection Modal in Apache Camel Kaoto

## Overview

In Kaoto ([KaotoIO/kaoto](https://github.com/KaotoIO/kaoto)), the open-source visual integration editor for Apache Camel, selecting a member for an XML `xs:choice` element with more than 10 candidates opened a narrow, single-column modal that clipped member descriptions, truncated child field previews at three items with no type information, and lacked any live inspection of selected schema options. To solve this, I redesigned `WrapperSelectionModal` into a two-pane resizable split view using PatternFly's `ResizableSplitPanels`, upgraded the candidate data model to supply full direct child field names and types, resolved vertical CSS collapse inside the modal container, and authored a comprehensive Vitest test suite. I opened Pull Request [#4385](https://github.com/KaotoIO/kaoto/pull/4385) resolving Issue [#3541](https://github.com/KaotoIO/kaoto/issues/3541); all automated CI checks and the SonarCloud quality gate passed, and the PR is currently awaiting human maintainer review.

## What happened

When I began reproducing the issue, I discovered that Kaoto's existing test schema (`ChoiceWithAbstract.xsd`) never triggered the selection modal at all. Reading `choice-field.service.ts` revealed why: the application enforces `INLINE_CHOICE_LIMIT = 10`. Choices with 10 or fewer members render directly inside the context menu, while only schemas exceeding 10 members launch `WrapperSelectionModal`. Because the repository had no fixture with 11 or more choice branches, I built a dedicated demo schema, `ChoiceModalDemo.xsd`, defining 12 complex choice members. Attaching it in the DataMapper debugger immediately reproduced the bug: a narrow, centered dialog where candidate descriptions were squeezed and child fields cut off after three names.

During implementation, my first attempt to embed PatternFly's `ResizableSplitPanels` into `ModalBody` failed visually: the entire split panel collapsed to nearly zero vertical height. Because `ResizableSplitPanels` uses percentage-based flexbox heights relative to its parent container, it collapsed inside PatternFly's standard `ModalBody`, which does not define an explicit height. Furthermore, rendering two panes inside a `medium` modal variant created severe horizontal cramping.

I changed my implementation by introducing a custom wrapper container class in `WrapperSelectionModal.scss` with an explicit height constraint (`height: 50vh; min-height: 300px;`), configured independent scrolling so that the search filter remains pinned while the candidate list scrolls, and upgraded the modal container to `ModalVariant.large`.

Here is the exact SCSS and JSX change from commit `4d436136`:

```scss
.wrapper-selection-modal {
  // ResizableSplitPanels fills 100% of its parent's height, so the body needs a fixed height
  // inside ModalBody; each pane then scrolls on its own.
  &__body {
    height: 50vh;
    min-height: 300px;
  }

  &__pane {
    height: 100%;
    overflow-y: auto;

    // Only the list scrolls, so the filter input stays visible in long lists.
    &--list {
      display: flex;
      flex-direction: column;
      overflow-y: hidden;
    }
  }
}
```

```tsx
<DataMapperModal variant={ModalVariant.large} isOpen={isOpen} onClose={handleClose} appendTo={() => document.body}>
  <ModalHeader title={title} description={description} />
  <ModalBody>
    <div className="wrapper-selection-modal__body">
      <ResizableSplitPanels
        defaultLeftWidth={45}
        leftPanelId={`${testId}-candidates-panel`}
        rightPanelId={`${testId}-details-panel`}
        leftPanelLabel="Candidates"
        rightPanelLabel="Candidate details"
```

Next, I tackled the data pipeline. The existing candidate contract (`IWrapperCandidate`) only carried `childrenPreview?: string[]`, which was generated by `WrapperBaseService.formatChildrenPreview` with a hardcoded `MAX_CHILDREN_PREVIEW = 3` cutoff and no type attributes. I refactored the interface to supply `children?: IWrapperCandidateChild[]` carrying `{ name: string; typeLabel: string }` objects, allowing the details pane to display complete field signatures.

Moving descriptions and fields from the candidate list rows to the right-hand details pane broke existing assertions that looked for field text inside list items. I rewrote the test suite in `WrapperSelectionModal.test.tsx` to verify empty states, selection updates, and type categories versus qualified schema types:

```tsx
it('should show an empty details pane when nothing is selected', () => {
  renderModal();
  const details = screen.getByTestId('test-modal-details');
  expect(within(details).getByText('Select a candidate to see its details.')).toBeInTheDocument();
  expect(screen.queryByText('Description for 0')).not.toBeInTheDocument();
  expect(screen.queryByText('child1')).not.toBeInTheDocument();
});

it('should show description and fields of the selected candidate in the details pane', () => {
  renderModal();

  fireEvent.click(screen.getByTestId('wrapper-radio-key-0'));

  const details = screen.getByTestId('test-modal-details');
  expect(within(details).getByText('Candidate 0')).toBeInTheDocument();
  expect(within(details).getByText('Description for 0')).toBeInTheDocument();
  expect(within(details).getByText('Fields')).toBeInTheDocument();
  expect(within(details).getByText('child1')).toBeInTheDocument();
  expect(within(details).getByText('child2')).toBeInTheDocument();
  expect(within(details).getByText('xs:int')).toBeInTheDocument();
});
```

Before opening the PR, an automated pre-check caught a silent drift in my PR draft: the draft summary stated that the empty details pane read *"Select a member to view its details."*, whereas my actual code and tests implemented *"Select a candidate to see its details."*. I updated the draft to match the codebase before publishing.

The results landed cleanly: maintainer `igarashitm` assigned the issue to me, and running the test suite across the four touched directories (`DataMapper`, `Document`, `visualization`, and `ResizableSplitPanels`) yielded 11 files and 190 modal/service unit tests passing (with 90 files and 1,930 tests passing across the wider affected areas), alongside clean lint, stylelint, and TypeScript compilation. I submitted PR [#4385](https://github.com/KaotoIO/kaoto/pull/4385), where all four CI checks passed, SonarCloud verified the quality gate, and CodeRabbit provided automated review feedback.

## Limitations and what's next

My current implementation intentionally renders only direct child fields (level-one children) of the selected candidate. If an XML choice member contains deeply nested complex sub-structures, the right pane does not recursively expand or traverse those sub-trees. CodeRabbit highlighted this boundary in its pre-merge review under a "Linked Issues" observation regarding expanded schema completeness. Additionally, abstract members nested inside a choice structure display a fallback note ("No additional details available.") because their candidate stubs carry only top-level name and type information. Finally, while `ChoiceModalDemo.xsd` was used to reproduce and test the fix locally, it has not yet been committed to the upstream repository stubs.

If maintainers decide they want deeper schema visibility, the next step would be implementing recursive schema traversal in `wrapper-base.service.ts` and adding an expandable tree component within the details pane. I would also contribute `ChoiceModalDemo.xsd` into `packages/ui/src/stubs/` so that automated regression tests for wide choice modals can run directly in Kaoto's continuous integration pipeline.
